# 1024 — Retry failed tasks

Claimed on `fix/1024-retry-failed-tasks` from clean `main`. Acceptance is the checklist in the task file. Ponytail 4.10.0 (MIT, full mode), workflow-and-kanban, Elixir/Phoenix LiveView, security-review, and quality-gates apply. XERJ project search was unavailable because the loopback node on port 9200 was not running; inspected the existing state machine and project workflow directly.

Initial trace: `TaskLive` renders no action for `blocked` and `failed`. `ProjectWorkflow.prepare_task/1` accepts only `ready` with no active run. `Transitions` already supports blocked run → failed (releasing `active_run_id`) and failed task → ready, but no command composes these with new-run preparation. A retry must preserve the old run's artifacts and avoid starting provider work implicitly.

Implementation: `ProjectWorkflow.retry_task/1` checks the latest eligible run and durable process records, closes a blocked run, returns its delivery task to Ready, and reuses `prepare_task/1`. Task detail has a LiveView Retry button; failed run detail links to it. Successful retry opens the new queued run without starting an agent. Previous run rows, events, artifacts, branch, and worktree remain unchanged. New run branches use the random tail of the UUIDv7 run ID because the earlier timestamp-prefix branch name collided on same-second retries. A failed queued preparation now records `run.preparation_failed`, marks that run failed, and leaves the task Ready for another attempt.
