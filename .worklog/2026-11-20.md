- Attempted `rtk proxy xerj search --prefix bossrefs "prompt task command natural language create task"` —
  local `xerj` node at `http://localhost:9200` unreachable; fell back to `rg` in
  `examples/` per `examples/README.md`.
- Queries & inspected sources:
  1. `rg --no-ignore -n "StartChat|chatBox|createTask" examples/kander examples/backlog examples/agetor`
  2. `examples/kander/AGENTS.md:39,96` (`https://github.com/dualface/kander` @
     `dea0ba6b885c39a56ee769223f7fa5c054e68c70`, MIT): TUI chat box (`StartChat` /
     `PreviewChat`) keeps draft input on failure, blocks duplicate submit while
     in flight, and drops stale async results by sequence, while never writing
     board state directly behind card transactions.
  3. `examples/agetor/docs/plans/at-file-references.md:30` & `branch-config-modal-button.md:26`
     (`https://github.com/alamops/agetor` @ `fbd68603afef778a618a94ca88e0c00997956afd`, MIT):
     server-authoritative `createTask` without materializing execution worktrees at
     creation time.
- Adopted pattern:
  - Read-only `:task_prompt` stage (`priv/task_prompt_schema.json`) executed via
    `Boss.Deliveries.Worker.run_agent/6` (`codex`, `claude`, `cursor`, `opencode`)
    with process-group guardian + `Stop` support, returning a strictly validated
    JSON action plan (`create_task`, `update_task_spec`, `block_task`,
    `needs_input_task`, `cancel_task`, `resume_task`, `retry_task`,
    `start_workflow`, `queue_workflow`, `cancel_queued_workflow`, `stop_workflow`).
  - Server-authoritative execution through existing `Projects.record_spec/2`,
    `Tasks.transition/2`, `Deliveries.start/5`, `Deliveries.Queue.enqueue/5`,
    `Deliveries.Queue.cancel/2`, and `Deliveries.stop/2`, keeping draft prompt on
    error and preserving user-explicit `check_command` + `reviewer` inputs.
- Rejected tradeoff:
  - Rejected letting an LLM run arbitrary shell commands, write directly to SQLite,
    or invent check argv / mark tasks `done` or `approved` without commit-bound
    delivery evidence.

## Increment 4 — `/projects/1` Autopilot Root-Cause Fix, Multi-Implementer Parallel Pool, `docs/` Breakdown Presets, Closed-Loop Reviewer Spec Rework → Backlog, & Live Animated Kanban Board

### Root-cause diagnosis (`http://localhost:4000/projects/1`)
- Inspected `/Users/mpak/.boss/boss.db` (`project_id = 1`, `uramawashi.com`):
  - Task 1 (`m0-bootstrap`: `"Phoenix foundation, deps, CI, dark shell"`) had delivery `7e8af107-1024-4c4a-a060-1f35ed2bc50b` in `status = "blocked"`, `cleanup = "group_empty"`, while `tasks.state` remained `"interrupted"` (`state_version = 22` vs `delivery.task_version = 21`) because `transition_changes/2` rejected `version + 1` after `complete:interrupted`.
  - Every remaining task (`Tasks 2..20`: `m1-auth` .. `m8-hardening`) depended on `m0-bootstrap` (`Task 1`).
  - Because `autopilot_recovery_candidates` excludes `state = 'interrupted'`, clicking **Start Autopilot** snapshotted only Tasks `2..20`, found `0` dependency-ready tasks, and immediately blocked the batch (`"No remaining task is ready..."`).

### Reference research (`examples/`)
- Query: `rtk proxy rg --no-ignore -n "max_parallel|concurrency|ChangesRequested|rework" examples/kander examples/backlog examples/agetor`
- Sources:
  1. `examples/backlog/packages/core/src/agents.ts:393-405` (`https://github.com/osmove/backlog` @ `3580cfbbb1be4144a5cca5b49190e1f8158e4cf7`, Apache-2.0): `rankAgentsForTask` counts only actively executing runs (`planning`/`implementing`/`testing`/`reviewing`) per agent binding rather than `ready_to_merge` runs parked for serialized integration, preventing pool starvation.
  2. `examples/kander/README.md:25` & `rules/KANDER-CODE-RULES.md:15` (`https://github.com/dualface/kander` @ `dea0ba6b885c39a56ee769223f7fa5c054e68c70`, MIT): conflict-aware bounded concurrency with explicit process-group ownership and bounded rework passes.
- Adopted pattern:
  - Least-busy / round-robin `Implementer` pool assignment (`project_implementer_pool` + `delivery_implementer_bindings`), parallel `Autopilot` worker dispatch up to `min(implementer_pool_size, Scheduling.capacity!())` with serialized `IntegrationWorker`, and bounded `SpecRework` (`max_passes: 2`) creating an immutable new `SpecRevision` + `task_entries` log + `adopt_revision` (`state = "new"`) before starting the next Autopilot loop pass.
- Rejected tradeoff:
  - Rejected mutating historical `autopilots`/`autopilot_items` rows in place or running unbounded paid rework loops.
